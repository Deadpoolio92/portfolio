01 // Architektur & Zerlegung

Weg mit dem „God-Prompt“: Warum monolithische Prompts scheitern

Die meisten Enterprise-KI-Workflows versuchen, einen einzigen „God-Prompt“ zu bauen. Sie kleben ein 50-Seiten-Handbuch, 20 API-Schemas und tausende Zeilen Code in einen riesigen Prompt und hoffen, dass die KI nichts kaputtmacht. In der Praxis knallt das gewaltig: Das Modell verliert den Faden und vergisst Regeln, die Kosten explodieren auf 34+ $ pro Session, und es nett zu bitten, keine Dateien zu löschen, ist Wunschdenken. So löst mein Conductor-Subagent-Mesh das Problem.

Die monolithische „God-Prompt“-Falle

Ein riesiger Kontext (80k–120k Tokens bei jedem Turn neu)

Ein Generalist • 300 KB Instruktionen beim Start geladen

Wie es die meisten machen: Eine einzige Generalisten-KI muss Produkt-Specs, Coding-Standards, Datenbank-Schemas und Terminal-Befehle gleichzeitig jonglieren. Jeder Follow-up-Turn sendet 80.000+ Tokens Ballast neu – das treibt die Kosten auf 34+ $ pro Session und löst Halluzinations-Schleifen aus.

  • Aufmerksamkeitsverlust: Die KI vergisst Regeln in der Mitte langer Prompts und fängt an zu halluzinieren.
  • Geld verbrennen: 50 Turns verbrauchen 6,85M Tokens – das kostet 34,25+ $ bei zähen 24 Sekunden Wartezeit.
  • Scheinsicherheit: Einen Agenten anzuflehen „bitte mach die Produktion nicht kaputt“ scheitert im Fehlerfall.
Karols Produktions-Standard

Autonomer Conductor + ephemere Single-Job-Subagenten

1 Task = 1 sauberes Fenster • Physisch entzogene Tools • Echte OS-Hooks

Wie Karol es baut: Ein autonomer Conductor zerlegt Arbeit in handliche Tasks, startet Single-Purpose-Subagenten mit physisch gekürzten Tool-Manifesten und verlangt zwei saubere Review-Durchläufe in Folge, bevor irgendetwas gemergt wird.

  • Frische Kontexte: Subagenten starten mit 0 Vor-Turns, fassen nur gebriefte Dateien an und enden danach.
  • 76,8 % weniger Tokens: Speicher bleibt flach bei ~4,2k Tokens, Session-Kosten sinken auf 7,95 $ und Latenz auf 4,8s.
  • Harte OS-Gates: Out-of-Band-PowerShell-Hooks stoppen gefährliche Befehle, bevor überhaupt eine Shell startet.

Der 4-Stufen-Lebenszyklus: Wie der Conductor Code ausliefert

Stufe 01

Task-Aufnahme & Scoping

Der Conductor zieht den nächsten Task per Questimus-REST-API, prüft Abhängigkeiten und erstellt ein klares Briefing.

Stufe 02

Frischer Builder-Spawn

Code Builder startet in einem frischen 0-Turn-Fenster, schreibt zuerst einen roten Test, implementiert sauber und beweist Grün.

Stufe 03

Consecutive Clean Pass Review

Zwei Review-Runden in Folge müssen 100 % fehlerfrei bestehen. Egal ob 2 oder 10 Runden – nichts wird gemergt, bis zwei Reviews am Stück komplett grün sind.

Stufe 04

Deterministisches Push-Gate

PreToolUse-Hooks prüfen Linter und Branch-Regeln vor dem atomaren Git-Commit und dem Schließen des Tickets.

02 // Least Privilege & Sandboxing

Physisches Tool-Stripping: Warum „Dateien nicht bearbeiten“ scheitert

Anfänger-Setups geben jedem Modell vollen Systemzugriff (Read, Write, Bash, Git, Netzwerk) und schreiben dann höflich in den Prompt: „Bitte Code nur prüfen, keine Dateien bearbeiten.“ Das ist ein schlechter Witz. Sobald ein Agent halluziniert oder auf einen Sonderfall stößt, bearbeitet er die Dateien trotzdem. Bei mir gilt physisches Tool-Stripping: Wenn ein Auditor-Agent nichts schreiben muss, wird write_file komplett aus seinem Manifest gestrichen. Selbst bei einer Prompt-Injection existiert das Tool für ihn schlicht nicht.

## Kaltes Review-Mandat & Null Schönreden
Du bist ein Staff-Level-Code-Reviewer beim Pre-Delivery-Review. Du weißt nichts darüber,
was die umsetzende Session wollte oder begründet hat. Du prüfst den Code kalt, so wie er ist.
Schwäche niemals Findings ab, weil der Code „zu funktionieren scheint“ oder „wohl passt“.

## Spezialisten-Dispatch (Standardmäßig aktiv — Paralleler Subagent-Swarm)
Entscheide zusätzlich zu deinen 7 Review-Dimensionen, welche Checklisten in
<AGENT_DIR>/resources/specialists/ relevant sind und starte JEDE als parallelen Subagenten:
- security.md        — Auth-/Session-/Token-/Rollen-Änderungen oder Backend-Diff > 100 Zeilen
- performance.md     — Algorithmische Komplexität, Hot-Path-Allokationen, unindexierte Filter
- red-team.md        — Feindliche Angriffsvektoren, stille Fehler, Trust-Boundary-Exploits
- error-handling.md  — Verschluckte Exceptions, unbehandelte Promise-Rejections, Recovery-Ketten
- api-contract.md    — API-/OpenAPI-/GraphQL-Breaking-Changes und Rückwärtskompatibilität
- data-migration.md  — Schema-/Migrations-Änderungen, Zero-Downtime-Rollbacks

Starte relevante Spezialisten in EINER einzigen Nachricht, damit sie parallel laufen.
Jeder Spezialist liefert striktes JSON: {"severity":"CRITICAL|INFORMATIONAL","confidence":N,"path":"...","line":N,...}
Führe die Ergebnisse in deinem 3-Tier-Output zusammen und dedupliziere über alle Quellen.

## Systemischer Pattern-Sweep (Pflicht bei Defekt-Fund)
Sobald du einen Regex- oder Algorithmus-Fehler (z. B. O(n²) oder schlechte Komplexität) meldest,
greppe sofort den REST der Codebasis nach demselben Muster, bevor die Runde endet.
Ein Fix in einer Datei heißt niemals, dass das Muster nicht noch woanders steckt.

## Runden-Vergleichs-Engine
Wenn ein Vorbericht vorliegt, tracke Statusübergänge explizit:
- ✅ CONFIRMED FIXED — was falsch war und nachweislich behoben ist
- 🟡 PARTIALLY FIXED  — was sich geändert hat, aber noch unvollständig ist
- 🆕 NEW INDEPENDENT — Problem, das durch den erweiterten Scope neu sichtbar wurde
- ⚠️ NEW REGRESSION  — Defekt, der direkt durch einen Fix der Vorrunde entstand

## Absoluter Branch- & Git-Lockdown
Arbeite auf dem im Briefing genannten Branch — erstelle, wechsle oder lösche niemals Branches.
DU MACHST NIEMALS git add, NIEMALS git commit, NIEMALS push.
Der Conductor prüft den Working Tree, staged und committet. Lass jede Änderung unstaged.

## Scope-Lock & Environment-Freeze
Baue NUR die im Task deklarierten Dateien. Falls der Task in dieser Liste wirklich nicht
lösbar ist, STOPPE und melde genau das — erweitere niemals eigenmächtig den Scope.
Fixes bleiben minimal innerhalb der Dateiliste; fremde Bugs werden gemeldet, nie gefixt.
Der Umgebungszustand des Conductors ist bindend: falls unmöglich, STOPPEN und melden.

## Pflicht: Red-Before-Green-TDD
Wenn der Task TDD vorschreibt: Schreibe zuerst den fehlschlagenden Test und zeige ihn ROT.
Der rote Test-Output MUSS in deine Evidenz kopiert werden — ein Red-before-Green-Anspruch
ohne einkopierten roten Output gilt als UNBEWIESEN und wird abgelehnt.

## Unverhandelbarer Output: DEBUG REPORT Block
Beende jeden Lauf exakt mit diesem strukturierten Block:

  **What was built**: <Zusammenfassung>
  **Files touched**: <Exakte Liste — muss mit deklarierten Dateien übereinstimmen>

  - <command> → <echter einkopierter Output, nur bei Überlänge gekürzt, nie zusammengefasst>

03 // Betriebssystem-Verteidigung

Nicht umgehbare OS-Hooks: Desaster stoppen, bevor die Shell startet

Sprachliche Guardrails (z. B. „Du bist ein hilfreicher Assistent. Führe keine destruktiven Befehle aus“) sind Wunschdenken. In komplexen Codebasen umgehen rekursive Fehlerschleifen, Prompt-Injections und Halluzinationen jede Textregel. Unsere Regel ist simpel: Vertraue niemals darauf, dass eine KI sich selbst kontrolliert. Deterministischer Code muss probabilistische Modelle steuern—setze ein echtes Skript vor das Modell, das die Tür hart zuschlägt.

PreToolUse-Interception-Architektur (JSON-IPC-Hook)

Stufe 01

Tool-Call-Anfrage

Autonomer Agent fordert Shell-Ausführung an (z. B. run_command("rm -rf ./build")).

Stufe 02

Payload-Interception

Harness fängt die Anfrage Out-of-Band ab und leitet das JSON-Payload per STDIN in security-gate.ps1.

Stufe 03

Deterministisches Regex-Audit

Hook prüft den Befehlsstring gegen 19 destruktive Regex-Signaturen (Force-Push, Disk-Wipes, Hard Resets).

Stufe 04

Exit-Code-2-Hard-Block

Destruktives Muster erkannt: Hook sendet Exit Code 2 an Stderr. Die OS-Shell startet gar nicht erst. Null Schaden möglich.

Aktiv geblockte Signaturen in Produktion (Exit Code 2 Hard Blocks)

Bedrohungskategorie Ziel-Signatur (Regex-Muster) Abgewehrtes operatives Risiko Hook-Aktion
Dateisystem-Löschung rm -rf, rm -fr, sudo rm Unwiderrufliches Löschen von Build-Assets oder Quellcode-Bäumen Exit Code 2
Git-History-Zerstörung git push --force, git push -f, git reset --hard Überschreiben der Remote-Commit-History oder ungesicherter Arbeit Exit Code 2
Branch-Verlust git branch -D Erzwungenes Löschen von Branches mit ungemergtem Produktiv-Code Exit Code 2
Working-Tree-Reset git checkout \., git restore \., git clean -f Stilles Verwerfen lokaler, uncommitteter Entwickler-Arbeit Exit Code 2
Datenbank-Zerstörung DROP TABLE, DROP DATABASE, TRUNCATE TABLE Katastrophales Löschen relationaler Tabellen in lokalen oder Container-DBs Exit Code 2
Host-Schäden & Fork-Bombs mkfs, dd if=, chmod -R 777, :\(\)\{:\|:&\};: Dateisystem-Korruption, Rechte-Entzug und Fork-Bombs Exit Code 2

Produktive PreToolUse-Hook-Implementierung (Verifiziertes PowerShell-Skript)

.agents/hooks/security-gate/security-gate.ps1 
# security-gate.ps1 — PreToolUse hook, blocks destructive Bash / run_command commands
# Hook event: PreToolUse -> bash | run_command
# Exit 2 = hard block (Claude Code/DSH); Exit 0 with decision: "deny" (Antigravity)

$ErrorActionPreference = 'Stop'
$InputJson = [Console]::In.ReadToEnd()

$cmd = ''
$isAntigravity = $false
try {
    $data = $InputJson | ConvertFrom-Json
    if ($null -ne $data.tool_input -and $null -ne $data.tool_input.command) {
        $cmd = [string]$data.tool_input.command
    } elseif ($null -ne $data.toolCall -and $null -ne $data.toolCall.args -and $null -ne $data.toolCall.args.CommandLine) {
        $cmd = [string]$data.toolCall.args.CommandLine
        $isAntigravity = $true
    }
} catch {
    $cmd = ''
}

# 19 Patterns that are hard-blocked regardless of context (case-insensitive)
$patterns = @(
    'rm -rf', 'rm -fr', 'git push --force', 'git push -f ', 'git push -f$',
    'git reset --hard', 'git clean -fd', 'git clean -f', 'git branch -D',
    'git checkout \.', 'git restore \.', 'DROP TABLE', 'DROP DATABASE',
    'TRUNCATE TABLE', 'DELETE FROM .* WHERE 1=1', 'mkfs', 'dd if=',
    'chmod -R 777', 'sudo rm', ':\(\)\{:\|:&\};:'
)

foreach ($pat in $patterns) {
    if ($cmd -match "(?i)$pat") {
        $msg = "BLOCKED by security-gate: destructive pattern detected ($pat)."
        [Console]::Error.WriteLine($msg)
        [Console]::Error.WriteLine("   Pattern: $pat")
        [Console]::Error.WriteLine("   Command: $cmd")
        [Console]::Error.WriteLine("   If this is intentional, run it manually in your terminal.")

        if (-not $isAntigravity) {
            exit 2 # Claude Code & DSH: Exit 2 halts execution immediately
        }
        @{ decision = "deny"; reason = "$msg Command: $cmd" } | ConvertTo-Json -Compress
        exit 0
    }
}

if ($isAntigravity) { @{ decision = "allow" } | ConvertTo-Json -Compress }
exit 0 # Verified clean: tool allowed

05 // State-Persistenz & Wiederaufnahme

Zustandslose LLMs, persistentes Gedächtnis: Kontext auf 0 Tokens leeren ohne Verlust

Large Language Models sind zustandslose Rechenmaschinen, keine Datenbanken. Wenn du 50 Runden Chat-Verlauf im Speicher hältst, läuft das Kontextfenster mit Müll voll und das Modell driftet ab. In meiner Architektur können wir den Kontext des Agenten jederzeit komplett auf 0 Tokens leeren, ohne eine Zeile Fortschritt zu verlieren. Jeder operative Zustand liegt extern in Questimus (unserem internen Projekt-, Ticket- und Tracking-Tool) per REST-API über ein sauberes Zweistufen-Modell.

Ebene 01: Makro-State

Die Projekt-HANDOFF-Seite

Speichert den übergeordneten Systemzustand, aktuelle Release-Version, aktiven Git-Branch, grüne Test-Suites und bekannte Fallstricke. Wird beim Session-Start automatisch gelesen und am Ende per REST festgeschrieben.

node questimus.js handoff • Stellt Session in <200ms wieder her
Ebene 02: Mikro-State

Atomare Ticket-Beschreibungs-Appends

Zwischenstände, rote Test-Outputs und Fix-Evidenz werden direkt an die aktive Ticket-Beschreibung angehängt (sicheres Description-only-Editing; nie uneditierbare Kommentare). Jeder frische Agent kann mitten im Task nahtlos übernehmen.

node questimus.js update <id> --desc-file .tmp/progress.md
